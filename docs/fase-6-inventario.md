# Fase 6 — Inventario (saldos, movimientos manuales y stock mínimo)

## Qué se hizo

1. **Módulo de Inventario** (`features/inventory`), primer módulo que no es un CRUD: el saldo (`InventoryResponse`) no se da de alta ni se edita directamente, se crea implícitamente con el primer movimiento y solo se consulta, se ajusta su stock mínimo o se mueve mediante entrada/salida manual:
   - Dominio (`core/domain/models/inventory.model.ts`, `core/domain/repositories/inventory.repository.ts`).
   - Infraestructura (`core/infrastructure/http/dtos/inventory.dto.ts`, `.../mappers/inventory.mapper.ts`, `.../repositories/inventory-http.repository.ts`).
   - Aplicación (`core/application/inventory/*.usecase.ts`): `SearchInventoryUseCase`, `GetInventoryUseCase`, `SetMinimumStockUseCase`, `RegisterInventoryEntryUseCase`, `RegisterInventoryExitUseCase`, `GetMovementHistoryUseCase`.
   - Presentación: `inventory-list` (saldos de una sucursal, HU-11), `inventory-entry`/`inventory-exit` (movimientos manuales sin documento de origen, HU-12/HU-13), `inventory-movements` (histórico auditable de un saldo, HU-14).
2. **Selector de sucursal solo para ADMIN**: `User.branchId` es `null` únicamente para ADMIN (RN-12, ámbito de organización completa); BRANCH_MANAGER/INVENTORY_OPERATOR tienen una sucursal fija. `InventoryListPage` usa ese campo para decidir: ADMIN ve un `<select>` de sucursales (pobladas con `SearchBranchesUseCase`, activas); los demás roles no ven selector, su sucursal ya está fijada — el backend igual la impone con 403 si se intentara otra, mismo criterio que ya documentó la Fase 2 para `branches.routes.ts`.
3. **La sucursal elegida viaja como query param (`?branchId=`), no como segmento de ruta**: `entries`, `exits` y `:productId/movements` son rutas propias sin `branchId` en el path porque, para BRANCH_MANAGER/INVENTORY_OPERATOR, la sucursal nunca varía (se lee de `AuthStore`) y no aporta nada codificarla en la URL; para ADMIN sí hace falta persistirla al navegar entre páginas del módulo, y un query param evita convertir todo el módulo en rutas anidadas por sucursal solo para cubrir un rol.
4. **`inventory.routes.ts` sin `roleGuard`**: a diferencia del catálogo (Categoría, Producto, Lista de precios, todos con alta/edición reservada a ADMIN), el inventario es trabajo operativo — cualquier rol autenticado necesita consultar saldos y registrar movimientos en su propia sucursal. El control real de alcance es el que ya aplica el backend por sucursal, no un rol de la UI.
5. **Edición de stock mínimo inline en el listado**, mismo patrón que el cambio de factor de una presentación en `ProductFormPage` (Fase 4): un botón "Editar mínimo" revela un input numérico en la misma fila, sin navegar a otra página, porque es un ajuste de un único campo (`SetMinimumStockRequest`).
6. **`InventoryMovementsPage` combina cabecera + histórico**: `forkJoin` trae en paralelo el saldo actual (`GetInventoryUseCase`) y los datos del producto (`GetProductUseCase`, para mostrar SKU/nombre) antes de listar los movimientos paginados — evita dos cargas secuenciales para una página que solo tiene sentido si ambas llamadas resuelven.
7. **`SKU`/nombre de producto resueltos en memoria en el listado de saldos**: `InventoryResponse` solo trae `productId`; en vez de pedir el producto uno a uno por fila, `InventoryListPage` precarga el catálogo activo (`SearchProductsUseCase`, tamaño 100) en un `Map<string, Product>` una sola vez, igual que ya hace `ProductListPage` con las categorías del filtro.
8. **Ruta y navegación**: `inventory.routes.ts` como hija lazy del shell en `app.routes.ts`; entrada en `NAV_ITEMS` de `AppShellComponent`, justo después de Panel — es la pantalla operativa de uso diario, no un catálogo de configuración, así que se ubica antes que Sucursales/Productos en el menú.
9. **DI**: `InventoryRepository` → `InventoryHttpRepository` en `app.config.ts`.
10. Verificado con `ng build --configuration development`: build limpio (browser + server); `inventory-list-page`, `inventory-movements-page`, `inventory-entry-page` e `inventory-exit-page` aparecen como chunks lazy independientes.

## Cómo se hizo (decisiones clave)

- **Sin alta/edición de `Inventory`, solo consulta y las dos mutaciones que la API expone**: modelar un CRUD aquí habría sido fabricar operaciones que el backend no tiene (`InventoryResponse` no tiene `POST`/`PUT` directo). El repositorio se ciñe a lo real: `search`, `getByProduct`, `setMinimumStock`, `registerEntry`, `registerExit`, `getMovementHistory`.
- **Entrada y salida como páginas separadas, no una sola con un toggle**: aunque comparten forma (`RegisterInventoryMovementRequest`: producto + cantidad + motivo), son semánticamente distintas (`RETURN_IN` vs. `LOSS_OUT`, HU-12 vs. HU-13, la salida puede fallar por stock insuficiente y la entrada no) — mismo criterio que ya separa `category-form` de `supplier-form` pese a tener campos parecidos: la duplicación entre dos flujos con significados de negocio distintos es más clara que una condicional dentro de un único componente.
- **Ajustes de inventario (`inventory-adjustments`, borrador + aprobación) y alertas (`inventory-alerts`, listado + descarte/resolución) quedan fuera de esta fase**: son flujos con su propio ciclo de vida (un ajuste se crea en borrador y se aprueba después; una alerta se dispara sola desde el backend y se descarta o resuelve) que no encajan en el patrón de movimiento inmediato de esta fase. Se documentan en "Qué sigue" en vez de forzarlos a la forma de `RegisterInventoryMovementRequest`, que no les corresponde.
- **`InventoryQuery` no tipa `sortBy` a un enum**: a diferencia de `ProductQuery`/`CategoryQuery`, `GET /branches/{branchId}/inventory` documenta `sortBy` como `string` libre en APIDOC.json, sin `enum` — forzar un tipo cerrado habría inventado una restricción que el backend no impone.

## Qué sigue (Fase 7 propuesta)

1. **Ajustes de inventario** (`POST /branches/{branchId}/inventory-adjustments` en borrador, `GET /inventory-adjustments/{id}`, `POST .../approval`): flujo de dos pasos — crear con líneas, aprobar después — pendiente de modelar como su propio caso de uso, no como variante de entrada/salida.
2. **Alertas de inventario** (`GET /inventory-alerts`, `POST .../dismissal`, `POST .../resolution`, HU-40): panel de alertas de stock bajo, con acciones de descartar/resolver.
3. Paneles del dashboard con datos reales (`/organizations/{organizationId}/dashboard/*`, incluido `product-rotation`) sustituyendo el placeholder de `DashboardPage`.
4. Pruebas unitarias: `ng test` sigue bloqueado en este entorno por falta de Chrome (`CHROME_BIN` no configurable aquí); pendiente para un entorno con navegador disponible.
